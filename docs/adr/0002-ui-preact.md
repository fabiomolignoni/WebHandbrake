# ADR 0002 — Preact and one hand-written stylesheet for the interface

- Status: accepted
- Date: 2026-10-04
- Requirements: MAINT-01, PERF-03, PERF-06

## Context and problem statement

WebHandbrake has four kinds of interface: the popup, which should open at once (PERF-06); the
dashboard, a single-page application with many pages and forms; the intervention page; and an
in-page overlay that the content script shows inside web pages. The extension's pages run under a
content security policy that allows only the extension's own scripts and styles. Store reviewers
read the shipped code, and contributors need a component model they can learn quickly.

Which way of building the interface fits these needs?

## Considered options

No prototype was built or measured; the comparison is qualitative.

1. **Svelte.**
   - Good: compiles components away, so the shipped code is small.
   - Bad: needs a compiler plugin in the build and its own component syntax. The shipped code is
     generated by the compiler and looks unlike the components.
2. **Lit (web components).**
   - Good: standard custom elements, small runtime.
   - Bad: styles are scoped to each component's shadow root, so one shared stylesheet with theme
     variables has to be adopted by every component.
3. **Plain DOM code.**
   - Good: no dependency at all.
   - Bad: a dashboard of this size needs hand-written updates of the page after every change of
     state, which is error-prone.
4. **Preact with hooks and JSX.**
   - Good: a small runtime with the component model of React, which many contributors know.
     esbuild compiles its JSX without a plugin.
   - Bad: a runtime dependency, and React's ecosystem works with it only through a compatibility
     layer, which is not used.

## Decision outcome

Chosen: option 4, Preact, with one hand-written stylesheet.

- Components are written in TSX with Preact's hooks. esbuild compiles them with the automatic JSX
  runtime (`jsxImportSource: 'preact'` in `scripts/build.mjs`) into one bundle per page: popup,
  dashboard and intervention page.
- Components shared by these pages live in `src/ui`; components used only by the dashboard live in
  `src/dashboard/components`.
- Styles are one hand-written stylesheet, `src/ui/styles/index.css`, built as `ui.css`, with CSS
  custom properties for themes and accent colours. There is no CSS framework and there are no
  remote fonts.
- **The content script does not use Preact.** The in-page overlay (`src/content/overlay.ts`) is
  plain DOM code in a closed shadow root: it runs inside every page it is injected into, so it
  stays small and isolated from the site's styles.

## Consequences

Good:

- `preact` is the only runtime dependency.
- Contributors who know React can read and write the components.
- The build needs no plugin: esbuild alone compiles TSX and CSS.

Bad:

- Each page's bundle contains its own copy of Preact and of the shared components, and the bundles
  are not minified ([ADR 0011](0011-auditable-build.md)), so the files are larger than they could
  be.
- Preact's published build is already minified, so that part of each bundle stays minified, and
  `web-ext lint` warns about its assignment to `innerHTML` (Preact's support for
  `dangerouslySetInnerHTML`, which WebHandbrake's code does not use).
- The popup's opening time and memory use (PERF-06) have not been measured
  ([verification debt](../roadmap.md#verification-debt)).
- Two folders hold components, and the overlay is styled separately from the stylesheet.

## Confirmation

- The `toolchain` check of `npm run docs:check` fails when the runtime dependencies in
  `package.json` are anything other than `preact`.
- Not automated: a reviewer checks that `src/content` imports neither Preact nor `src/ui`.
