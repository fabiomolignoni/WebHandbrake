# ADR 0005 — In-house ICU messages instead of browser.i18n

- Status: accepted
- Date: 2026-10-04
- Requirements: I18N-01, I18N-02, I18N-03, SET-02

## Context and problem statement

Every interface string must be translatable, with plural forms and context for translators
(I18N-01), and the person must be able to choose the interface language in the extension's
settings (SET-02). The WebExtension API `browser.i18n` reads messages from `_locales`, but it always
follows the browser's language and has no plural rules.

How are interface strings stored and formatted?

## Considered options

1. **`browser.i18n` and `_locales` for everything.**
   - Good: built into both browsers, no code to maintain.
   - Bad: the language cannot be chosen in the extension, and plurals need one message per form
     with the choice made in code.
2. **An ICU MessageFormat library**, such as FormatJS.
   - Good: complete and maintained, with dates, ordinals and every plural category.
   - Bad: a second runtime dependency ([ADR 0002](0002-ui-preact.md) keeps `preact` the only one),
     added to every page's bundle.
3. **WebExtension-format message files formatted by a small in-house ICU formatter.**
   - Good: the language can be chosen, plurals follow `Intl.PluralRules`, and the files use the
     layout that translation platforms read for extensions.
   - Bad: the formatter covers only the part of ICU that the messages use, and it is code to
     maintain.

## Decision outcome

Chosen: option 3.

- Interface strings live in `src/locales/<language>.json`, in the WebExtension layout: a `message`
  and, where the context is not obvious, a `description` for translators. `src/_locales` holds
  only what the manifest needs: the name, the description and the keyboard command descriptions.
- `src/i18n/icu.ts` formats `{name}` arguments, `{n, number}`, `plural` (with `=n` cases and `#`)
  and `select`, with `Intl.PluralRules` and `Intl.NumberFormat`.
- English is bundled. Another language is fetched from its file when chosen in **Settings ›
  General › Language**, and missing keys fall back to English one by one. `AVAILABLE_LOCALES` in
  `src/i18n/i18n.ts` lists the languages that ship.
- The in-page overlay receives the raw messages and formats them inside the page, so that
  placeholders are filled where the values are known.
- `npm run i18n` (`scripts/check-i18n.mjs`, part of `npm run check`) checks that every key used in
  the code exists in `src/locales/en.json`, that every message has balanced braces, that each
  `t()` call with literal parameters passes every placeholder of its message, and that
  `AVAILABLE_LOCALES`, the files in `src/locales` and the folders in `src/_locales` agree.

## Consequences

Good:

- The language is a setting of the extension, independent of the browser's.
- Plural forms are written in the message, so translators can follow their own language's rules.
- Adding a language takes a message file, a manifest folder and one line in `AVAILABLE_LOCALES`
  ([CONTRIBUTING.md](../../CONTRIBUTING.md#translate)).

Bad:

- Only English ships, so **Language** offers **Same as the browser** or English.
- Right-to-left support is partial: the page direction is set for Arabic, Persian, Hebrew and Urdu,
  but the stylesheet still uses some physical left and right properties, and no right-to-left
  rendering is tested.
- No translation platform has been tried with these files.
- The formatter supports neither dates nor ordinal plurals (`selectordinal` is read with cardinal
  rules). A missing parameter renders as empty text; `npm run i18n` catches it only in calls whose
  parameters are an object literal.

## Confirmation

- `npm run i18n` runs in CI as part of `npm run check` and fails on the problems listed above.
